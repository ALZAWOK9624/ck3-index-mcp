# 从零建库的进一步优化（2026-09-05）

本文为当时版本的实验记录。后续 [审查修复](AUDIT_FIXES_20260906.md) 将活动库写入与可丢弃 stage 的同步策略分开，并修正内容校验、诊断依赖和计时命名；下列数字没有冒充新版本的复测结果。

本轮接续 [索引重建与刷新优化](INDEX_REFRESH_PERFORMANCE_20260905.md)，针对 `scan --clean` 的实际批量写入与索引创建。常规完整刷新仍保留上一轮的全输入哈希、复用派生数据和隔离发布。

## 保留的修改

- 批量写入对象、引用、字段、本地化、saved scopes 和 variables 时，在当前扫描事务内复用完整批次的预编译语句。只缓存六种固定形状；文件末尾的不满批次正常执行，文件大小变化不会导致缓存不断增长。事务结束释放语句，缓存不跨扫描或解析线程共享。
- 从零扫描的二级索引在已调优的专用写连接上用一个事务创建，保留该连接的缓存设置，避免通过读取连接池逐个索引提交。失败时整个索引创建事务回滚。

没有改变输入集合、诊断规则、批次大小、索引定义或数据耐久性设置。已有用户修改和此前几轮优化一并提交；本轮新增的实现仅涉及 `scan_batch.go`、`scan.go`、`scan_files.go` 和 `bulk_indexes.go`。

## 实测

Windows amd64，原生 C 路径和原生 SQLite：`-tags "ck3_native sqlite_fts5"`。相同的隔离项目副本及只读依赖层；69,321 个文件，25,525,937,628 字节，每个文件实际读取并哈希。所有数据库与生成缓存均为实验副本。

| 项目 | 上一轮基线 | 本轮最终方案 |
| --- | ---: | ---: |
| 从零建库总耗时 | 97.143 秒 | 92.052 秒 |
| 批量写库阶段 | 14.234 秒 | 11.339 秒 |
| 创建二级索引 | 15.496 秒 | 13.244 秒 |

与本次系列优化最初的 114.989 秒相比，最后一次从零建库实测少约 22.94 秒（19.9%）；相对上一轮少约 5.09 秒（5.2%）。这些是**单次实际运行记录，不是稳定中位数或性能承诺**。从零建库意味着没有旧数据库可复用，并不意味着操作系统文件缓存被清空。读取、解析和写入存在重叠；磁盘、地图处理和缓存波动也会改变总耗时。上一轮基线少一个测试用脚本，不影响上述数量级，但两次输入并非逐字节相同。

本轮中间版本：只合并索引创建事务时 97.501 秒；加上 SQL 复用和未采纳的 FTS 合并实验时 95.323 秒。最后版本撤回 FTS 实验后为 92.052 秒，写库阶段在两次包含 SQL 复用的运行中分别为 12.072 和 11.339 秒。

## 未采纳的实验

尝试过调整本地化 FTS5 的 `automerge`、`crisismerge`、`pgsz`，导入后 `optimize`，再恢复增量维护设置。内存实验从约 18 秒降到约 12 秒，但完整磁盘建库中 FTS 阶段仍约 24.4 秒，收益不足以支持保留更复杂的流程，已撤回。

参数含义参考 [SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html#the_automerge_configuration_option)。内存微基准的收益不直接当作用户实际建库收益。

## 校验与复现

新增回归比较预编译与原路径在完整批次、短批次、多次调用下的实际存储结果，并确认事务回滚后没有残留记录。其余完整扫描、增量刷新、发布和搜索的现有测试继续覆盖实际调用路径。

- 原生 SQLite 和默认纯 Go SQLite 的全仓测试均通过，两者 `go vet` 均通过。
- 新增批量写入、完整扫描、压缩搜索相关用例的原生 race 检查通过。
- 真实数据库 39 张表规范化逐行摘要中，38 张完全一致；`map_titles` 仅 `center_x/center_y` 有原有浮点累加顺序造成的尾差，最大绝对差 `5.9117155615240335e-12` 像素，其余字段完全一致。本轮没有改地图中心计算。
- 八组实际中英文、空白、标点查询与原路径及精确 `instr()` 对照结果一致。搜索比较只用于确认结果，未将顺序执行造成的缓存差异作为查询性能收益。
- 最终原生程序在实验库执行 `health --require-ready` 成功，深度健康检查为 `ok`；新增脚本定义可以通过正式 CLI 查询。

复现入口：`go run -tags "ck3_native sqlite_fts5" ./cmd/scan-perf -config <配置> -scratch <隔离目录> -database <实验库文件名> -mode clean`。必须先在 scratch 下准备 `project` 副本；不要指向日常运行库。

本地实验记录位于 `cache/perf-cold-20260905/`：`accepted.json` 为最终冷建库统计，`index-tx.json` 和 `final.json` 为中间实验；`semantic-parity.json`、`search-parity.json` 为真实数据核对；`tests-native.log`、`tests-default.log`、`tests-race.log` 为测试日志。此目录被 Git 忽略，不上传真实索引数据。

最终原生程序输出为 `bin/ck3-index-native-cold-perf.exe`。这次上传源码，不自动替换正在运行的 MCP 进程；重新构建并用新程序启动服务后才会使用新实现。
