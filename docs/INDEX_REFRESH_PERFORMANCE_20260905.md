## 实测结果

使用当前真实配置的全部上游来源，并把项目层复制到隔离目录。所有写库、文件修改、索引发布都发生在 `cache/perf-index-20260905/`，没有修改正式项目、共享基础索引或当前 MCP 使用的数据库。

基线：69,320 个文件，25,525,937,481 字节输入；238,596 个对象，1,086,087 条引用，2,694,889 条本地化，43,902 个资源，299 条诊断。

| 操作 | 优化前 | 优化后 | 说明 |
| --- | ---: | ---: | --- |
| 常规完整刷新，输入未变化 | 114.99 秒 | 14.99 秒 | 原配置的基础索引过旧，旧程序重新建库；新程序复用兼容的已发布索引，但仍重新读取、哈希全部输入 |
| 新增一个脚本后完整刷新 | 原完整重建基线 114.99 秒 | 24.21 秒 | 使用最终可执行程序；读取并哈希全部 69,321 个文件，只解析新增的 1 个文件，成功查询到新定义 |
| 从零建库 | 114.99 秒 | 97.14 秒 | 单次实测，约减少 15.5% 等待时间；包含文件缓存与磁盘波动，不能把复用路径的倍数套用于冷建库 |
| 指定一个修改过的小脚本刷新 | 6.178 秒 | 2.160 秒 | 交替执行三轮的中位数，约 2.86 倍 |
| 指定一个未修改的小脚本刷新 | 2.100 秒 | 0.332 秒 | 同上，约 6.33 倍 |

完整刷新不是恒定 15 秒。复制数据库、系统文件缓存、文件变化量、地图输入变化都会影响时间。已测的两次复用分别约 15 秒和 24 秒；地图或大量依赖文件变化会需要更多工作。

三轮修改刷新原始耗时（毫秒）：旧版 `7327, 6001, 6178`，新版 `2153, 2160, 2377`。无变化刷新：旧版 `2100, 2087, 2160`，新版 `330, 332, 336`。两版使用相同的修改后文件，交替执行顺序。

## 实现

1. **完整刷新复用上一代索引。** 优先检查已发布索引的就绪状态、完整输入身份、提取/诊断规则、引擎指纹、表结构和已记录的语义行数。通过 SQLite 在线备份得到一致副本，再次检查副本后执行全来源扫描。包括二进制资源在内的所有文件重新计算内容哈希，禁止复用路径依靠大小和时间戳跳过读取。未变化的派生记录、地图缓存和 FTS 可以保留；删除、新增和覆盖关系改变仍由现有扫描器重算。最终保留原有隔离发布、并发锁、失败保留旧代的行为，并为新快照生成新的 revision。
2. **`scan --clean` 真正强制从零重建。** 跳过已发布索引和 `base_database` 两种复用路径。常规刷新返回 `reused_generation` 和 `seed_staged` 耗时；总耗时现在也包含备份和发布。
3. **避免全文索引健康检查反复遍历虚拟表。** 使用 FTS5 维护的 docsize 行号表统计文档数；本地化行数相等加单向行号包含检查证明行集合相等，仍能识别缺失、清空、以及等数量的伪造行号。选择从较小的本地化覆盖索引查 docsize，避免反向访问宽表。
4. **人物姓名本地化按需检查。** 用预编译查询检查真正出现的姓名 key，在本次检查内缓存结果；不再为一个小文件刷新装载数百万条本地化 key。缓存不跨刷新保留，因此补充或删除本地化仍立即反映在诊断中。
5. **地图省份历史一次读取。** 把文化、宗教、holding 的时间序列读入内存，通过二分查找取书签日期前最后的有效值，替代每县、每日期、每字段重复发 SQL。无值、空值、`holding=none` 的诊断规则保留。
6. **压缩本地化子串索引。** 新建 trigram FTS 使用 `detail=none`，仅保存 token 的文档归属。查询求最多八个三字符片段的交集，再用原始值的 `instr()` 精确过滤，保持大小写、字符顺序、引号、空白和重复字符的实际匹配语义。新版查询兼容旧的完整位置索引，现有索引无需为了这个改动立即重建。健康探针也同步适配。

trigram 数据块有效载荷从 **485,661,662 字节降到 173,795,120 字节**，约缩小 64.2%；docsize 载荷不变。实验数据库文件从约 2.857 GB 降到 2.536 GB。数据文件尺寸会随空闲页和后续增量写入波动。

首次建库阶段：地图缓存 `25.69 → 18.45 秒`，语义 FTS `31.61 → 23.84 秒`，全局诊断 `2.19 → 0.38 秒`。阶段并非全部可以简单相加，读取、解析与写库部分存在重叠。

## 正确性与兼容性

- 原生 SQLite 全仓测试通过：`go test -tags "ck3_native sqlite_fts5" ./...`。
- 默认纯 Go SQLite 全仓测试通过：`go test ./...`。
- 原生版本 `go vet ./...` 通过；发布复用、并发刷新、压缩搜索及边界用例的 race 检查通过。
- 新增回归覆盖：删除项目覆盖后恢复上游、取消 descriptor 的 replace_path、依赖层内容改变、新增被引用定义、资源内容改变但大小和时间戳不变、显式 clean、损坏或不兼容快照回退、两种 trigram 格式的随机 Unicode/引号/空白搜索、空 token 文档、等数量伪造 FTS 行号、省份历史日期边界。
- 对两个真实数据库做 39 张表的规范化逐行摘要比较。**38 张完全一致**，包括文件、对象、引用、本地化、资源、字段、诊断、语义搜索记录和大部分地图表。
- `map_titles` 仅有 `center_x/center_y` 的浮点尾差，最大绝对差 `9.094947017729282e-12` 像素，其余字段完全一致。原有 `insertMapStatic` 遍历 Go map 并累加浮点中心；该函数所在的 `map_context.go` 本轮字节未变。报告保留原始差异，没有把它写成逐字节相同。
- 真实库的八类中英文、标点查询，对照旧位置索引、新压缩索引和纯 `instr()` 查询，返回结果一致；另有生成式测试覆盖更多字符组合。
- 最终程序在隔离库运行 `health --require-ready` 成功，状态 `ok` / `ready`，FTS5 可用；新增脚本的定义确实可查。

复用检查不是任意数据库篡改的逐行校验器。手工改库、需要强制重算全部派生结果时使用 `--clean`。新压缩格式需要新版查询代码；退回旧程序前应从旧版可读的数据库备份恢复，或用旧程序重新建库。本轮没有测试 Linux 实机。
