# 完整刷新与 FTS 局部刷新性能记录（2026-09-07）

本轮实现完整刷新无变化时复用已发布代、按文件到 FTS rowid 的映射删除局部文档，并补齐冷建库子阶段计时。真实原生后端测量中，无变化 full 的中位数从 17.907 秒降到 12.722 秒，单文件改动的 files 刷新从 2.147 秒降到 1.752 秒。冷建库尚未加速，有改动的 full 在这批样本中反而变慢；下表保留这些成本。

## 结果

| 场景 | 次数（每版） | 基线中位数 | 候选中位数 | 耗时变化 |
| --- | ---: | ---: | ---: | ---: |
| full，无内容或元数据变化 | 5 | 17.907 s | 12.722 s | -29.0% |
| full，单个脚本内容变化 | 5 | 20.152 s | 23.078 s | +14.5% |
| files，单个脚本内容变化 | 5 | 2.147 s | 1.752 s | -18.4% |
| files，文件无变化 | 5 | 0.308 s | 0.323 s | +15 ms |
| files，501 个消费者依赖被修改定义 | 5 | 5.162 s | 4.787 s | -7.3% |
| clean，从零建库，第一版候选 | 3 | 91.520 s | 94.836 s | +3.6% |

无变化 full 仍然逐个读取并验证全部文件内容，哈希数量和字节数没有减少。它跳过复制整库、建临时代及发布，峰值工作集中位数由约 502 MB 降到 328 MB；进程逻辑写入中位数由约 2.533 GB 降到 4.2 KB（后者是报告等进程输出，数据库保持只读）。测试另行确认数据库字节摘要、代号和发布身份保持不变。

单文件 files 的 FTS 删除不再扫描整张虚拟表。代表性样本中，该部分由约 350 ms 降到不足 1 ms；整个刷新仍包含加载符号、诊断与提交，不能把删除阶段的比例当成整体加速。

完整扫描发现改动时，需要支付只读预检后再执行原有隔离扫描。本组元数据变化样本的预检约 0.65–0.72 秒；整库复制同时存在数秒波动，因此不能把 +14.5% 全部归因于预检，也不能忽略实测退步。若内容变化刻意保留大小和时间戳，预检可能先做哈希才拒绝，随后隔离扫描还会再读一次；正确性优先，尚未实现跨预检复用这些读取。

无变化 files 多约 15 ms，与新增映射完整性计数有关。冷建库的 FTS 映射构建约 0.9–1.1 秒，三次数据库大小中位数由 2,532,552,704 增至 2,569,703,424 字节，约增加 37.2 MB。映射和其索引增加了一次性构建及存储成本。

## 实现与一致性边界

`search_documents(fts_rowid, file_id)` 在同一事务内跟随 FTS 重建、增量删除和插入更新，普通索引 `idx_search_documents_file` 支持按文件定位 rowid。删除前验证所选映射对应的 FTS 文件身份，避免错误映射删除引擎文档或其他文件；尾部 rowid 重用、零分词文档和回滚均有回归覆盖。缺失映射或文档数不一致会失效重建。数量相同不是对任意手工损坏的完整证明，所选行的身份校验仍然必要。

full 的只读预检与普通扫描共享来源遍历、覆盖与文件选择逻辑。目录枚举得到的元数据只用于快速拒绝；接受无变化需要全量内容哈希、读取前后文件身份检查、规则与输入兼容、地图依赖和缓存检查，以及发布身份的最终比较。取消和并发发布不会被当作成功。无法证明安全复用时回到隔离扫描；`clean` 始终重建。

真正复用时返回 `noop=true, reused_generation=true, committed=false`，MCP 不再宣称发生提交。仅元数据变化时仍可提交更新，即使语义 `noop=true`；调用方应以 `committed` 判断是否发布。现有工具结果没有增加兼容格式；修正了刷新输出声明里原本漏掉的三个已有字段，并同步维护指南。

升级前的数据库没有 FTS 映射。首次完整升级可能需要重建一代；首次局部刷新也可能重建规范 FTS 与映射。主表的重复刷新收益是在这项初始化完成后测得，不能承诺首次升级也同样快。

## 验证

最终候选在完成全部刷新和 501 消费者依赖切换后，对两库进行了完整规范化比较：去除代理 ID、通过来源和相对路径关联，再对排序后的行计算 SHA-256。39 张原有表中 38 张完全一致，包括文件、对象、引用、本地化、资源、字段、诊断、作用域、变量、地图关系与 FTS 全文。`map_titles` 只有浮点中心坐标末位差异，最大绝对差 `6.821210263296962e-12` 像素，其余字段和行数相同。新增映射与全部 1,588,641 条 FTS 文档的 rowid/file_id 对应一致。

此外，9 个包含英文、中文、标点和空白的搜索查询，两版结果一致；长查询的 trigram 筛选与精确文本查询对照，短查询核对直接文本筛选。搜索对照只用于结果一致性，不以先旧后新的单次查询耗时宣称搜索加速。501 个消费者的定义连续切换五次，每次全部引用状态和完整诊断集合一致，并保留大范围影响时的全局解析回退。结果见 [REFRESH_PARITY_20260907.json](REFRESH_PARITY_20260907.json)。

本地验证完成：默认与原生后端全仓测试、两种后端 `go vet`、原生相关竞态测试、生成文档检查及 skill 校验。最终元数据优化提交另跑了完整刷新、无变化、隔离扫描、并发刷新与 FTS 相关回归及原生竞态检查；GitHub CI 状态以对应提交的检查页为准。

验证过程中保留的环境问题：高并发 Go 编译曾遇到 Windows 分配内存失败，限制编译并发后全仓测试通过；已有跨进程打包测试曾出现一次 Windows ZIP 文件共享冲突，连续三次单独重跑及后续两种后端全仓测试通过。本轮未修改打包器，不能据此声称修复了该偶发问题。

下一轮应优先研究 trigram 构建、地图派生/物理层和全量读取；full 有改动的额外预检与整库复制也需要单独压低。若做诊断依赖收窄，应先考虑 error-log contract 与 folder schema，并继续保持大范围影响时的全局回退。本轮没有更改这些阶段的算法，也没有用关闭检查或手写汇编替代它们。

## 复现入口

使用同一 Go 工具链和配置分别构建两个 Git tree 的 `cmd/scan-perf`，原生构建同时提供 `ck3_native sqlite_fts5` 两个标签。将项目复制到隔离目录的 `project` 子目录，保留上游来源只读。基线 tree 没有此命令时使用本变更中的相同驱动文件，只更换所链接的 indexer 实现。

```powershell
go build -trimpath -buildvcs=false -tags "ck3_native sqlite_fts5" -o scan-perf.exe ./cmd/scan-perf
.\scan-perf.exe -config <workspace-config> -scratch <isolated-dir> -database after.sqlite -mode clean
.\scan-perf.exe -config <workspace-config> -scratch <isolated-dir> -database after.sqlite -mode full
.\scan-perf.exe -config <workspace-config> -scratch <isolated-dir> -database after.sqlite -mode files -file common/scripted_triggers/zz_perf_refresh_probe.txt
```

在副本中创建一个 41 字节脚本，交替使用 `perf_refresh_probe = { is_alive = yes }` 与等长 `no ` 值；每次更改后对两版执行相同模式，无变化样本不再修改文件。完整冷建库至少三对，其余场景至少五对，按轮交换先后顺序。另一次 clean 可加 `-profile <output.cpu.pprof>`；它只用于定位热点，单独报告。
